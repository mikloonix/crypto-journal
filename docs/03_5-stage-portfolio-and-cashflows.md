# Этап 3.5 — Портфель (ввод/вывод) и equity от депозитов

Цель этапа: вести учёт **пополнений/выводов** по торговому аккаунту и строить «кривую капитала» относительно реального депозита/кэша, а не фиксированной константы `JOURNAL_INITIAL_DEPOSIT_USDT`.

## Решения (зафиксировано)

- **Счёт (`Account`):** не расширяем валютой/биржей под этот этап. Счёт — «ящик» для сделок и денежных движений; как в текущей Prisma-схеме (`name`, `isDefault`, `source`, …).
- **Валюта операции:** только у **`Cashflow`**: `currency` и при необходимости `fxRate` (приведение к USDT).
- **Отчётность:** на текущий момент все агрегаты и кривые **только в USDT** (как PnL по сделкам).
- **Область equity:** как в журнале — по **выбранному счёту** или по **всем счетам** (тот же фильтр, что и у списка сделок).
- **Переводы между счетами:** **в scope этапа 3.5**; в таблице cashflow должно быть однозначно видно движение между счетами.
- **Стартовый капитал (MVP):** только **ручной ввод** (например первая операция пополнения с нужной датой или отдельный сценарий в форме — деталь реализации). Импорт с биржи и эвристики «последнее пополнение при нуле» — не в MVP.

## Definition of Done

- Есть страница `/portfolio`.
- Пользователь может вести **cashflow-операции**:
  - пополнение (deposit);
  - вывод (withdrawal);
  - **перевод между аккаунтами** (transfer).
- Для каждой операции сохраняются:
  - дата/время (UTC в БД);
  - сумма;
  - валюта;
  - курс к USDT при необходимости (`fxRate`, если `currency` ≠ USDT — правила валидации на API);
  - комиссия (опционально);
  - заметка.
- **Equity curve** на дашборде и в аналитике согласована с cashflow:
  - стартовый баланс в USDT = кумулятивные пополнения − выводы (+ учёт переводов в выбранной области «счёт / все счета») на соответствующую дату;
  - далее кривая = баланс после cashflow до точки + кумулятивный реализованный PnL по закрытым сделкам + события cashflow в хронологическом порядке (единая серверная логика, без дублирования в UI).
- `Cashflow` привязан к `userId` и к счетам согласно типу операции (см. ниже).

## Модель данных (целевая для реализации)

- **`Account`:** без изменений под «базовую валюту» в рамках 3.5 (см. решения выше).
- **`Cashflow`:**
  - `id`, `userId`;
  - `type`: `DEPOSIT` | `WITHDRAWAL` | `TRANSFER`;
  - для **DEPOSIT** / **WITHDRAWAL:** основной счёт операции (`accountId`);
  - для **TRANSFER:** явно зафиксировать в схеме связь **двух** счетов (например `fromAccountId` + `toAccountId`, либо пара строк с общим `transferGroupId` — выбрать один вариант при миграции Prisma и не смешивать);
  - `amount` (число > 0);
  - `currency` (строка);
  - `fxRate` (опционально; для отчёта в USDT обязателен/подразумевается 1, если валюта USDT — правила в Zod/API);
  - `fee` (опционально, в той же логике конвертации, что и сумма);
  - `timestamp`;
  - `note` (опционально).

## UI/UX

- Таблица операций с фильтрами по периоду (скоуп журнала: счёт / все счета).
- Колонки: **Сумма** (тело в валюте операции), **Комиссия**, **Итог** (нетто в USDT).
- Карточки: **Пополнения за период** (net cashflow за фильтр), **Депозит** (оценка баланса в скоупе), **PnL** (закрытые сделки в скоупе).
- Быстрое добавление / редактирование операции (включая перевод).

## Риски

- Если считать equity без cashflow, график вводит в заблуждение при пополнениях/выводах и переводах.
- Переводы требуют строгих инвариантов (сумма «вышла» с одного счёта и «вошла» в другой в одной логической операции), иначе двойной учёт или дыры в балансе.

## Реализация (код)

- **Prisma:** модель `Cashflow` + enum `CashflowType` (`DEPOSIT` | `WITHDRAWAL` | `TRANSFER`); перевод — одна запись с `fromAccountId` / `toAccountId`.
- **Расчёты:** `src/server/trading/cashflow-usdt.ts` (USDT), `equity-timeline.ts` (equity журнала и кривая аналитики); без дублирования в UI.
- **API:** `GET|POST /api/cashflows`, `PATCH|DELETE /api/cashflows/[id]`; ответы в envelope проекта.
- **UI:** `/portfolio` — таблица, период, форма; дашборд/журнал/аналитика используют тот же скоуп счёта, что и журнал (`journalAllAccounts` / `activeAccountId`).
- **Миграции:** `20260515100000_stage35_cashflows`. На существующей БД без `_prisma_migrations` — baseline, см. `04-stage-risk-management.md` (раздел Prisma).

### Legacy: DEP/WITH без `accountId`

- В БД поле `Cashflow.accountId` может быть `null` у старых строк. API создания DEP/WITH по-прежнему **требует** `accountId`.
- При журнале **одного счёта** такие строки учитываются в equity **только если** это счёт совпадает с **дефолтным** пользователя (`Account`: `isDefault` или первый по списку — `findDefaultAccountId`).
- Реализация: `JournalEquityScope.legacyCashflowAccountId`, фильтр выборки в `cashflow-repository.ts`, дельта в `cashflowPortfolioDeltaUsdt` (`cashflow-usdt.ts`); проброс скоупа в журнал, дашборд, аналитику, портфель, risk evaluate / sync-balance.
