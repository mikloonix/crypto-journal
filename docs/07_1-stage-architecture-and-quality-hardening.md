# Этап 7.1 — Укрепление архитектуры и качества (ответ на техдолг)

**Зависимости:** этап **2.3** ([`02_3-stage-architecture-and-api-consistency.md`](./02_3-stage-architecture-and-api-consistency.md)), действующие правила в `.cursor/rules`.

**Цель:** убрать зоны, где внешний аудит помечал проект как «частично», «возможно», «риск» — зафиксировать границы слоёв, снизить риск гонок и нагрузки, выровнять валидацию и ошибки, заложить минимальный контур тестов. Пункты, которые **уже не относятся** к репозиторию (например `userId` из query в аналитике, отсутствие `force-dynamic` на API), в DoD отмечены как **N/A — уже соблюдено**.

## Связь с замечаниями аудита

| Тема (аудит) | Было | Цель 7.1 |
|--------------|------|----------|
| Размытые слои / fat frontend | Частично | Явные правила + декомпозиция страниц, API только из `features/*/api` / хуков |
| «Нет домена» / только JSON | Частично | Документировать SSOT: Prisma + `contracts/*`; при необходимости — тонкий `src/domain/*` только типы/инварианты без Prisma в UI |
| Валидация входа API | Частично | Zod на все мутации trading/settings, единый ответ ошибок |
| State / гонки загрузки | Возможно | AbortController или request generation; единый паттерн для списков и аналитики |
| Error handling / Prisma | Частично | `mapPrismaError` + стабильные сообщения; не «PATCH error» без контекста |
| Лимиты аналитики | Риск | Макс. диапазон дат, опционально лимит CSV |
| Тесты | Да (отсутствуют) | Минимальный набор unit + CI |
| `lib/` разрастается | Риск | Соглашение по каталогам в этом документе + ревью |
| Сессия / черновик сделки | UX-риск | Черновик формы в `sessionStorage` + `beforeunload` на критичных формах |
| TZ / UTC | Уже ок паттерном | Док-тест: один сценарий границы дня; явная формулировка в `AGENTS.md` |

## Definition of Done (чеклист)

### A. Границы архитектуры (документ + код)

- [ ] В [`AGENTS.md`](../AGENTS.md) или [`02_3-stage-architecture-and-api-consistency.md`](./02_3-stage-architecture-and-api-consistency.md) добавлен блок **«Границы слоёв (обязательно)»**:
  - `app/api/*` — только auth, parse query/body, вызов service, envelope-ответ.
  - `src/server/services/*` — оркестрация, без прямых «сырых» запросов в обход repository (кроме явных исключений в доке).
  - `src/server/repositories/*` — Prisma, везде фильтр `userId` из аргументов.
  - `app/**/page.tsx` (client) — UI + вызов хуков; **без** формул PnL и **без** прямого `fetch` к `/api` (только через `src/features/*/api.ts` или общий клиент).
- [ ] Проведён **аудит** страниц: `app/analytics/page.tsx`, `app/dashboard/page.tsx`, `app/trades/closed/page.tsx` — вынесены хуки (`useAnalyticsScreen`, `useDashboardTrades`, …) в `src/features/trades/hooks/` или рядом; цель: файлы страниц < ~300 строк логики или разбиты по секциям.

### B. Валидация (Zod)

- [ ] Создан каталог `src/server/validation/` (или `shared/schemas` согласно этапу 7, если объединяете) со схемами:
  - открытие сделки, закрытие, удаление (если body), PATCH trading defaults (уже частично на сервисе — расширить единообразно).
- [ ] Каждый **POST/PATCH** trading и критичный settings вызывает `schema.safeParse`; при ошибке — `400` + `{ success: false, error: "..." }` с полями Zod (или агрегированное сообщение), без утечки стека.

### C. Ошибки Prisma и API

- [ ] Файл `src/server/http/prisma-errors.ts` (имя по согласованию): функция `toClientError(e: unknown): { message: string; status: number }` с разбором **P2002, P2025, P2003, P1001** и fallback.
- [ ] Route handlers: в `catch` для мутаций использовать маппер; убрать голый `PATCH error` без классификации там, где ещё осталось.

### D. Гонки и актуальность данных

- [ ] Для **хотя бы** журнала сделок и аналитики: при смене query / счёта / вкладки — отмена устаревшего запроса (`AbortSignal`) или игнор ответа по монотонному `loadId` (ref + сравнение перед `setState`).
- [ ] Документировать в коде (короткий комментарий у хука) выбранный паттерн — один на проект для списков.

### E. Нагрузка и аналитика

- [ ] В `analyticsService` (или repository): **максимальный диапазон** календарных дней (например 366 или 731) от `fromYmd`/`toYmd`; при превышении — `400` с понятным текстом.
- [ ] CSV: опционально **лимит строк** или тот же cap по датам; зафиксировать в доке.

### F. Тесты и CI

- [ ] Добавлен **Vitest** (или Jest) в `package.json`; скрипт `npm run test`.
- [ ] Минимум тестов:
  - `calculateTradePnL` / критичный путь из `risk-manager.ts` (2–3 кейса: long/short, fee);
  - один тест на **границу дня** (`zoned-date-range` или эквивалент) с фиксированным TZ;
  - опционально: парсинг envelope в `api-fetch`.
- [ ] В CI (GitHub Actions или аналог) шаг `npm run test` + `npm run build` (если CI ещё нет — завести минимальный workflow в рамках 7.1 или отослать к 5.5 с явной ссылкой).

### G. UX сессии и форм

- [ ] На форме **открытия сделки** (dashboard): при изменении полей — сохранение черновика в `sessionStorage` (ключ `draft-open-trade` + user id); при успешном POST — очистка; при монтировании — восстановление с подтверждением или тихо.
- [ ] `beforeunload` при несохранённых изменениях (опционально, если не конфликтует с UX).

### H. Каталог `src/lib/` (анти-свалка)

- [ ] В этом документе или в `AGENTS.md` таблица: **куда класть новый код** — `lib/trading/*`, `lib/format/*`, `server/trading/*` и т.д.
- [ ] Запрет: новые «общие» утилиты без привязки к домену в корне `lib/` — только в подпапку по теме.

### I. Уже не задача 7.1 (зафиксировать как N/A)

- **Утечка `userId` через query в `/api/analytics`** — в коде используется сессия; DoD: «проверено, не менять контракт без security review».
- **Отсутствие `force-dynamic` на API** — у критичных route уже есть; периодический grep в CI опционально.
- **Гонка двух пользователей на один числовой ID сделки** — используются cuid; не вводить автоинкремент без миграции.

## Порядок работ (рекомендуемый)

1. **Документ границ** (п. A) — 0.5 дня, без ломки фич.
2. **Prisma errors + валидация** (B, C) — снижает поддержку и баги API.
3. **Лимиты аналитики** (E) — быстрый win для продакшена.
4. **Abort / loadId** (D) — по одному экрану (analytics → journal).
5. **Декомпозиция страниц** (A код) — итеративно по PR.
6. **Vitest + 3 теста** (F).
7. **Черновик формы** (G).
8. **Соглашение lib/** (H) + лёгкий рефактор переноса только при касании файлов.

## Риски

- Чрезмерный рефакторинг UI в одном PR — дробить.
- Zod-дубли с этапом 7 — позже слить в `shared/schemas`; в 7.1 допустимо `src/server/validation` с пометкой «мигрировать в shared при этапе 7».

## Тест-план приёмки 7.1

- [ ] Любой POST с невалидным телом → 400 и понятное сообщение.
- [ ] Двойной быстрый выбор периода на аналитике → нет «мигания» старых данных поверх новых.
- [ ] Диапазон аналитики 10 лет → отказ с сообщением.
- [ ] Обновление страницы с заполненной формой открытия → черновик восстанавливается (если включено).
- [ ] `npm run test` зелёный локально и в CI.
