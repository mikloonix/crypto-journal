# Этап 2 — Домен “Сделки/Трейды” + Журнал (core value)

Цель этапа: реализовать правильную доменную модель (spot/futures, открытие→закрытие, группировка в трейды) и удобный журнал сделок (таблица + карточки) с фильтрами по периоду.

## Definition of Done

- Пользователь создаёт **открытую** сделку (Trade) по нажатию “ввод сделки”
- Поддержаны **несколько входов/выходов** по одной монете в рамках одного Trade
- Закрытие Trade фиксирует `closedAt` (по кнопке подтверждения/условиям объёма)
- Журнал умеет группировать:
  - по дням/неделям/месяцам/кастомному периоду
- Есть быстрые фильтры: монета, стратегия, статус (OPEN/CLOSED), рынок (SPOT/FUTURE)
- Все CRUD операции защищены и работают только с `userId`

## Данные (рекомендуемая минимальная модель)

Если придерживаемся текущей Prisma-идеи (`Trade` + `Entry/Exit`), то надо дополнить поля под ТЗ:

- **Trade**:
  - `symbol` (выбор из списка пар)
  - `marketType` (SPOT/FUTURE)
  - `direction` (LONG/SHORT)
  - `strategy` (строка/справочник)
  - `emotionEntry`, `emotionExit`
  - `notes`
  - `fee`, `funding` (суммарно по трейду или агрегировать из операций)
  - `createdAt`, `closedAt`
- **Entry**:
  - `timestamp` (ставится автоматически “по нажатию”)
  - `price`, `volume`, `leverage`
  - `reason`/`setup` (опционально)
- **Exit**:
  - `timestamp` (автоматически “по нажатию подтверждения”)
  - `price`, `volume`
  - `fee`, `funding` (если нужно точнее — лучше на уровне операций)

Важно: решить, где хранить комиссии/фандинг:

- **простое**: на уровне Trade (как сейчас в Prisma)
- **точное**: на уровне Entry/Exit (и агрегировать)

## API контракты (примерный набор)

- `POST /api/trades` — создать Trade + первый Entry
- `POST /api/trades/:id/entries` — добавить Entry
- `POST /api/trades/:id/exits` — добавить Exit
- `POST /api/trades/:id/close` — закрыть Trade (фиксирует `closedAt`, `status`)
- `GET /api/trades` — список с фильтрами (период/статус/символ/стратегия)
- `DELETE /api/trades/:id` — удалить Trade целиком

## UI/UX (журнал)

- **Таблица** (desktop):
  - символ, направление, рынок, статус
  - средняя цена входа, средняя цена выхода
  - размер позиции/объем
  - PnL $ и %, комиссии, фандинг
  - длительность
- **Карточки** (mobile):
  - компактные данные + действия (добавить выход/вход, закрыть)
- **Быстрое создание**:
  - тикер выбирается из списка (см. этап 5/интеграции — биржевые пары)
  - время входа — автозаполнение (серверное время), но показывать в UI
  - валидаторы (zod) и обработка ошибок

## Расчеты

Нужно централизовать расчеты (один модуль/один источник):

- PnL на основе операций `Entry/Exit`, с учетом direction (LONG/SHORT)
- комиссии и funding
- ROI % относительно используемого депозита (определить правило: от `RiskSettings.accountBalance` или фиксированного initial balance)

## Тест-план (минимум)

- Создание Trade + Entry
- Добавление частичного выхода и проверка пересчета PnL
- Закрытие Trade и появление в “Closed”
- Фильтрация по датам и символу

## Риски

- Если не решить модель комиссий/фандинга сейчас, аналитика позже будет “кривой”
- Времена событий: лучше ставить на сервере, иначе будут расхождения между устройствами
